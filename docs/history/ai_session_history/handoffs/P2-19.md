# P2-19 — Consolidate clients

## Planner

Duplicate Binance HTTP/WS clients were the unfinished P3/TODO item 19.

Inventory:
- `BinanceFuturesClient` (signed, EndpointGuard) vs `BinanceFuturesRESTClient` (hardcoded production public REST)
- `BinanceFuturesWSClient` (used by data feed) vs unused `BinanceFuturesWebSocket`
- `BinanceExchangeFilterCache` and `MarketScannerEngine` each opened their own httpx sessions against a hardcoded production host

Out of scope: Redis singleton (already consolidated), Telegram/journal/notifier (different APIs).

## Builder

One REST client (`BinanceFuturesClient`) owns the HTTP session and EndpointGuard URL.
Public market-data methods never call assert_can_submit_order and never send API keys.
Signed methods still fail closed before any network I/O.
`BinanceFuturesRESTClient` is a subclass facade.
`BinanceFuturesWebSocket` is an alias of the canonical WS client.
WS URL is an official REST→WS map on EndpointGuard; unknown hosts fail closed.
Filter cache and scanner share the REST client; order manager shares one client with the filter cache.
